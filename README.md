# 分支剧情一致性审校台（Branching Story Auditor）

一个用于检查 **分支剧情 / 互动叙事脚本一致性** 的 Web 应用。支持为每个场景设置 **布尔前置条件、进入时状态赋值**，为每个选项设置 **显示条件、状态赋值、跳转目标和正整数权重**，并指定剧情起点。后端会从起点出发，按 **「场景 + 变量状态」组合状态** 进行穷举传播与去重，因此即使剧情包含环路（可反复返回的场景），分析也保证终止。基于同一状态图，还可以对编辑中的草稿做 **结局概率推演**：精确求解各终止场景的最终到达概率，并单独列出永远困在循环中的概率质量；生成 **选项覆盖路线**：用确定性贪心集合覆盖压缩出一组可执行路线，让所有实际可走的选项至少被走一遍；分析 **结局必经抉择**：精确求出每个可达终止场景的全部到达路线共同经过的稳定选项（含环、同场景多状态仍精确终止），并给出必经次序、最短见证路径与绕开反例查询；做 **伏笔回收路线校验**：选择铺垫场景与回收场景后，把「待回收」标记并入状态遍历，找出到达设计结局时伏笔仍未回收的最短违规路线；做 **节奏校验**：勾选高强度场景并设置允许的最长连续场景数（1～10），把「连续高强度计数」并入状态遍历（进非高强度即清零、环路中逐圈累计），找出连续高强度场景超限的最短路线并展示沿途场景、变量状态与连续计数；求解 **结局保证到达**：选定目标结局（无选项场景）并指定哪些场景由环境控制后，用最小不动点反向扩展判断是否存在玩家策略，使环境任意选择合法选项都能在有限步内到达目标，成功时给出每个获胜玩家状态的推荐选项与保证层级，失败时给出环境反制见证（非目标死局 / 可无限停留的循环 / 目标不可达）；以及做 **变量赋值消费审计**：把「每个变量最后由哪处赋值写入」并入状态遍历，逐处检查场景进入赋值与选项赋值写入的值在再次被赋值或路线结束前是否被后续条件引用，为已消费项给出到首次引用的最短可走路线。

## 能发现什么问题

| 类型 | 含义 |
| --- | --- |
| **不可达场景** `unreachableScene` | 从起点出发，不存在任何选项链能进入该场景（孤岛场景 / 唯一通路选项恒假 / 入口前置冲突） |
| **条件永不成立的选项** `neverTrueOption` | 选项所在场景可达，但在所有能到达的变量状态下，该选项条件都为 false，玩家永远看不到它 |
| **悬空跳转** `orphanOption` | 选项没有目标，或跳向不存在的场景 ID |
| **入口前置冲突** `blockedEntry` | 选项本身可触发，但目标场景的前置条件在跳转后的变量状态下恒不成立（赋值与前置条件互相矛盾） |
| **结构 / 语法错误** | 未指定起点、场景 ID 重复或缺失、条件表达式语法错误、引用未声明且从未赋值的变量等 |

点击任一问题，右侧会展示：

1. **最接近的可达路径**：从起点到问题点的最短选项链（含每一步的变量状态）；
2. **未满足的条件解释树**：逐层标注每个子条件的期望值 / 实际值，并给出 **最少只需翻转哪些变量** 即可让条件成立，帮助定位是哪条状态赋值缺失或冲突。

## 一条命令启动（需要 Docker + Docker Compose）

```bash
docker compose up -d --build
```

这一条命令即可完成全部工作：构建镜像时按 `package-lock.json` 精确安装依赖（`npm ci --omit=dev`），
启动容器时自动完成初始化（数据目录为空则播种示例剧情），并启动页面服务。

启动后访问：

> **http://localhost:3000**（容器内监听 `0.0.0.0:3000`，Compose 映射到宿主机 `3000` 端口；需改宿主机端口时编辑 `docker-compose.yml` 中 `"3000:3000"` 的左侧值）

首次启动且数据目录为空时，会自动写入一份示例剧情 **《失落王权》**（其中刻意包含循环、不可达场景、恒假条件、悬空跳转等缺陷，方便直接体验审校功能）。

停止：

```bash
docker compose down          # 保留剧情数据（Docker 卷 story-data）
docker compose down -v       # 同时删除剧情数据卷
```

查看日志：

```bash
docker compose logs -f
```

容器内置健康检查：Compose 会在容器内运行随镜像分发的 Node 探针
`scripts/healthcheck.js`（仅使用 Node 内置模块，无第三方依赖）。探针**固定通过
`127.0.0.1`** 请求 `GET /api/stories`——此前使用 `wget http://localhost:...`
时，部分环境会把 `localhost` 解析到 IPv6 的 `::1`，而应用监听的是 `0.0.0.0`
（IPv4），导致服务正常却被误判为 unhealthy。探针仅在请求在超时内返回 **2xx**
且响应体可解析为 **JSON 数组**时退出 0；连接失败、超时、非 2xx 或响应体畸形
均退出非 0。探针超时由 `HEALTHCHECK_TIMEOUT_MS` 控制（默认 4000ms，小于
Compose healthcheck 的 5s 超时）。

## 条件表达式语法

选项条件与场景前置条件使用布尔表达式：

- 变量名：以字母 / 下划线开头，仅含字母、数字、下划线，如 `hasKey`；
- 与 / 或 / 非：`a && b`、`a || b`、`!a`；
- 括号：`(a || b) && !c`；
- 留空表示 **恒真**；
- 未定义的变量按 `false` 处理；若变量既未在“布尔变量”中声明、也从未被任何赋值设置，分析结果会额外给出警告。

## 剧情 JSON 格式（同时也是导入 / 导出格式）

```json
{
  "title": "剧情标题",
  "description": "可选简介",
  "startScene": "village",
  "variables": [
    { "name": "hasKey", "description": "是否持有钥匙" }
  ],
  "scenes": [
    {
      "id": "village",
      "title": "宁静村",
      "text": "场景正文……",
      "precondition": "",
      "assigns": [],
      "options": [
        {
          "text": "走进森林",
          "condition": "!hasKey",
          "target": "forest",
          "weight": 2,
          "assigns": [{ "variable": "hasKey", "value": true }]
        }
      ]
    }
  ]
}
```

- 场景 `assigns`：**进入场景时** 执行的赋值（包括从起点进入）；
- 选项 `assigns`：选择该选项时执行的赋值，随后再执行目标场景的进入赋值；
- 选项 `weight`：可选的 **正整数权重**（1、2、3…；缺省视为 1，保存时缺省不落盘该字段），用于「结局概率推演」中同一状态下可走选项的选择占比；0、负数、小数、字符串等非法权重会在 **保存 / 导入 / 推演** 时得到带场景与选项位置的明确校验错误（HTTP 400）；
- 选项 `uid`：可选的稳定身份标识，基线对比用它识别“同一条选项”（不随选项拖动重排而变）；留空时保存会自动生成；
- 顶层 `baseline`：分析基线快照（由「保存分析基线」生成，也可随导入 JSON 携带，无效快照会被忽略）；
- 起点场景的初始变量状态 = 全部为 `false` 再叠加起点场景自身的进入赋值。

导入通过页面右上角 **「⬆ 导入 JSON」** 完成（导入总是创建一份新剧情，不会覆盖现有内容）；导出使用 **「⬇ 导出 JSON」** 或接口 `GET /api/stories/:id/export`。

## 分析原理（为什么含循环也能终止）

分析器把每个可达局面编码为 `(场景 ID, 全部布尔变量的取值位图)`：

1. 以起点场景 + 其进入赋值后的状态作为初始具体状态；
2. BFS 遍历：对当前具体状态下的每个选项求值条件——成立则应用选项赋值与目标场景的进入赋值，得到新具体状态；
3. 新状态按 `场景 + 状态位图` 去重，已访问过就不再入队。

布尔变量数为 n 时，具体状态总数至多为 `场景数 × 2^n`，必然有限，所以任意循环都不会导致分析发散（设有约 100 万状态的安全上限，超限会在结果中提示“分析截断”）。

“条件永不成立”的判定：若某选项 **被到达过**，但在所有到达它的具体状态下条件都不成立，则该选项对玩家不可见；只要存在任意一个可达状态使条件成立，即视为正常。

## 分析基线（对比修订前后）

在右栏「一致性分析」中可以把**当前分析结果保存为基线**，随后继续编辑剧情并随时「运行对比」：

| 对比状态 | 含义 |
| --- | --- |
| **新增** `new` | 基线时不存在、当前分析中出现的问题 |
| **已修复** `fixed` | 基线时存在、当前分析中已消失的问题 |
| **仍存在** `persistent` | 同一条问题仍在，路径与文案也没有变化 |
| **详情变化** `changed` | 同一条问题仍在，但**最短可达路径或问题文案发生了变化**；详情面板中可用「当前路径 / 基线路径」标签对照前后路径，文案变化则同时展示基线与当前两版消息 |

对比结果上方有差异摘要（各类计数）与按状态筛选的按钮；对比之后若继续编辑，会提示「对比结果可能过期」，重新运行对比即可。

**稳定指纹（为什么重排场景 / 选项不会错配）**：后端为每条问题生成一个不依赖任何数组顺序的指纹，身份要素为：

- 问题类型（不可达场景 / 悬空跳转 / 入口冲突 / 恒假选项 / 结构错误）；
- 场景 ID、**选项稳定 UID**（随剧情持久化，保存旧剧情时自动回填；导入的旧数据缺失时用 `场景ID#数组下标` 兜底）；
- 关键目标场景 ID（如悬空跳转指向的目标）。

指纹只对这些身份要素做规范化 JSON 序列化（对象键排序）后取 SHA-1，路径、文案、变量状态等易变内容不参与指纹，因此移动场景顺序、调整选项排列、修改正文都不会让同一条问题被误判为“新增”。

基线快照（保存时间、问题指纹、前后对比所需的路径与消息）以 `baseline` 字段**随剧情 JSON 一起持久化**，导出 / 导入 JSON 时一并携带；删除剧情即删除基线，也可单独「删除基线」。保存基线会同时把当前草稿落盘，保证基线与保存内容一致。

## 目标路径查询

编辑页右侧的「目标路径查询」面板回答另一类问题：**“怎样走才能在依次经过指定选项、绕开禁用选项的前提下，到达某场景并让指定变量为真 / 为假？”**

1. 选择 **目标场景**，并可添加若干条 **到达约束**（变量 = true / false；不添加约束则只要求到达目标场景）；
2. 可添加若干 **有序必经选项**：按选项的 **稳定 UID** 从场景分组下拉框中选择，列表次序即路径中必须依次经过的次序，可用 ↑ / ↓ 调整；再可选若干 **禁用选项**（查询时这些选项不可走）；
3. 后端在「场景 + 完整变量状态」的具体状态空间上执行 **可终止的 BFS**（与分析器相同的状态去重与约 100 万状态上限），并把 **“已完成的必经序号”纳入去重键**——同一局面在不同必经进度下视为不同节点，“先绕路完成必经项再返回”的路线不会被错误合并；禁用选项不扩展；只有 **依次经过全部必经项**、且到达目标场景时 **满足全部变量约束** 才算命中，返回 **最短选项链及每步状态**（每个场景节点带到达时的完整变量取值，每条选项边带选择后的状态，完成某个必经项的边标注「必经 N」）；
4. **无解时**返回与目标 **差异最少的可达状态**（目标场景上的到达状态优先，其次“缺失变量数 + 未完成必经项数”更少、路径更短）、**缺失变量清单**（变量、期望值、实际值）、**未完成必经项清单**（序号、场景、选项文案）以及到达该状态的 **最近路径**；目标场景本身不可达时，回退到全剧情中最接近约束的可达状态并明确标注；
5. 若搜索因 **状态上限被截断**，结果以 `canAssertUnsolvable: false` 标明 **不能断言无解**（只有完整穷举后才敢下“无解”结论）；
6. 查询针对的是 **编辑中的草稿**（不落盘）；剧情或查询条件（目标、约束、必经 / 禁用选择与次序）被修改后，旧结果会标记为 **可能过期**，重新「查询路径」即可。

**API 校验（返回 400）**：必经选项与禁用选项不得冲突（同一 UID 不能同时出现在两者中）；列表中的每个 UID 都必须在当前剧情中存在（编辑器新建的选项会立即预分配 UID，保存时由服务端保留）；同一变量的到达约束、同一列表中的 UID 均不可重复。

响应要点：`found`（是否命中）、`depth`（选项链长度）、`path`（场景/选项交替的每步状态，必经边带 `requiredOrder`）、`finalState`、`requiredOptions` / `disabledOptions`（回显的选项明细）、`unfinishedRequiredOptions`（未完成必经项）、`completedRequiredCount`；无解时 `closest`（差异最少状态、缺失变量 `missing`、未完成必经项 `unfinishedRequiredOptions`、差异数 `mismatchCount`、最近路径 `path`）、`canAssertUnsolvable`、`truncated`、`statesExplored`。

## 结局概率推演

编辑页右侧的「结局概率推演」面板回答：**“按选项权重随机游玩，最终到达每个结局的概率各是多少？有多大比例会永远困在循环里？”**

1. 为选项设置 **正整数权重**（编辑器选项卡片中的「权重」输入框，缺省为 1）；权重随剧情 JSON 保存、导入与导出；
2. 点击「推演结局概率」，后端对 **编辑中的草稿**（不落盘）展开「场景 + 变量状态」图（与分析器相同的 BFS 去重与约 100 万状态上限）；
3. **每个具体状态下，仅对「条件成立且目标可进入」的选项按权重归一化**：条件不成立、目标场景不存在（悬空跳转）、或应用赋值后目标前置条件不成立的选项不参与归一化；指向同一状态的选项权重合并；
4. **含环图精确求解，不用固定步数截断冒充结果**：用 Kosaraju 找出全部闭合类（底 SCC），对瞬态子链精确求解线性方程组 `(I − Q)X = B`（高斯消元 + 部分主元，多右端一次解出），得到各终止场景的 **最终到达概率**；状态数超出稠密求解上限时改用 Gauss-Seidel 迭代求解同一方程组，**收敛到容差内才输出**，不收敛则明确报告；
5. **永远困在循环中的概率质量单独列出**：含内部边的闭合类（陷阱循环）按进入概率汇总，并给出涉及的循环场景；没有任何可走选项的状态是吸收态——场景本身无选项记为 **结局**，有选项但全部不可走记为 **死局**（软锁）；
6. 状态空间超上限被截断时 **不输出概率**（避免以不完整的状态图冒充结果），只返回明确的截断说明；剧情被继续编辑后，旧结果标记为 **可能过期**，重新推演即可。

响应要点：`endings`（`sceneId` / `title` / `kind`：`ending` 或 `deadend` / `probability` / 吸收态数 `states`，按概率降序）、`totalEndingProbability`、`loopProbability`、`loops`（每个陷阱循环的 `probability`、涉及的 `scenes`、包含的具体状态数 `states`）、`counts`（具体状态数、转移数等）、`solver`（`exact` / `iterative` / `trivial`）、`conditionErrors`（语法错误按恒真处理的计数）。任意一次完整推演都有 `totalEndingProbability + loopProbability = 1`。

## 结局必经抉择

编辑页右侧的「结局必经抉择」面板回答：**“无论玩家怎么走，要到达某个结局，必定要选哪些选项？它们的先后次序如何？首次到达该结局的最短路线长什么样？”**

1. 点击「分析必经选项」，后端对 **编辑中的未保存草稿**（不落盘）展开「场景 + 完整变量状态」具体状态图（与分析器相同的 BFS 去重与约 100 万状态上限）；
2. 终止具体状态 = 该状态下没有任何「条件成立且目标可进入」的选项：场景本身无选项记为 **设计结局**（`ending`），有选项但全部不可走记为 **死局软锁**（`deadend`）；**同一场景可能对应多个不同变量状态的终止节点**；
3. **必经判定不是枚举固定深度路径**：某选项 UID 对结局必经，当且仅当**每一条**从起点到该结局任一终止状态的路线都经过它。后端在「能到达该结局的存活子图」上做选项标签数据流的最大不动点 `F(v) = ⋂（F(u) ∪ {边标签}）`（起点为空集，其余以全集初始化、按逆边 worklist 单调收缩），结局必经 = 各终止节点 `F(t)` 的交集。取值在有限标签幂集上只做集合交，单调下降，所以**含任意环路都必然收敛终止**；同场景多状态由终止节点交集正确处理；
4. 每个结局展示：**必经选项的先后次序**（所有必经选项都出现在每条到达路线上，次序取「首次到达」BFS 最短见证路径上的首次出现位置）、**首次到达的最短见证路径**（场景节点带完整变量状态，必经选项边标注「必经 N」）；
5. **绕开反例**：从该结局可达子图的选项中任选一个，可请求一条**不经过该选项**仍到达该结局的最短路线。非必经选项必然能找到反例；对必经选项，完整穷举后仍不可绕开时明确回复「确为必经」；
6. **状态上限截断时不下任何必经结论**：结果以 `canAssertForced: false` 标明，已发现的结局标记 `reliable: false` 并隐藏必经列表与反例请求（未探索区域可能存在推翻结论的路线）；绕开查询在截断时也以 `canAssertUnavoidable: false` 标明不能断言必经；
7. 分析针对编辑中的草稿；**草稿或起点变化后，旧结果标记为「可能过期」**，重新「分析必经选项」即可。

响应要点：`canAssertForced`（是否可下必经结论）、`truncated`、`counts`（状态数、转移数、`forcedOptions`：截断时为 `null`）、`endings[]`（`sceneId` / `title` / `kind`：`ending` 或 `deadend` / `reliable` / 终止状态数 `states` / `forcedCount` / `forcedOptions[]`：`order`、`uid`、`sceneId`、`optionIndex`、`text`、`target` / `candidateOptions[]`：该结局可达子图上的非必经选项（绕开反例候选）/ `witnessDepth` / `witnessPath` / `finalState`；截断时结论字段为 `null`）。绕开接口响应要点：`found`（是否存在反例）、`depth`、`path`、`finalState`、`canAssertUnavoidable`（完整穷举后仍不可绕开才为 `true`）、`truncated`。

## 选项覆盖路线

编辑页右侧的「选项覆盖路线」面板回答：**“至少要跑哪些路线，才能让每条实际可走的选项都至少被走一遍？”**

1. 点击「生成覆盖路线」，后端对 **编辑中的草稿**（不落盘）展开「场景 + 变量状态」图（与分析器相同的 BFS 去重与约 100 万状态上限，循环图按具体状态去重，必然终止）；
2. 选项在某个具体状态下 **可走** = 条件成立 且 目标场景存在 且 应用赋值后目标前置条件成立。首次观测到某选项可走时的前驱状态即它的 **见证**：从起点到见证状态的最短选项链 + 该选项本身，构成一条 **可复现路线**——每条可走选项都先各自保留一条；
3. 再用 **确定性的贪心集合覆盖** 压缩路线集：每轮选出「新覆盖未覆盖选项最多」的见证路线，平分时取见证发现顺序最早者（无随机性，同一草稿多次生成结果完全一致），直到全部可走选项被覆盖；
4. 每条路线列出 **选项 UID、经过的场景与每步状态**（场景节点带到达时的完整变量取值，选项边带选择后的状态），并标注该路线 **新覆盖** 与 **累计覆盖** 的选项 UID；
5. **覆盖分母只含实际可走的选项**：场景不可达、条件恒假、入口前置恒受阻、悬空跳转的选项一律不计入分母，单独列出并标注原因（`unreachableScene` / `neverTrue` / `blockedEntry` / `orphan`）；
6. 状态数超上限被截断时结果标记为 **不完整**（`complete: false`）：已发现的可走选项仍被完整覆盖，但未探索区域可能还有可走选项，且「不可走」判定降为暂定（`excludedOptions` 中 `definitive: false`）；
7. 生成针对的是编辑中的草稿；剧情被继续修改后，旧结果标记为 **可能过期**，重新「生成覆盖路线」即可。

响应要点：`coverage`（`coverable` 分母 / `covered` 已覆盖 / `rate` 覆盖率）、`counts`（选项总数、路线数、具体状态数等）、`routes`（每条含 `depth`、`covers` / `newlyCovered` 选项 UID 数组、`path` 每步场景与状态）、`excludedOptions`（未计入分母的选项及原因）、`complete` / `truncated`、`conditionErrors`。完整（未截断）时必有 `covered = coverable`、`rate = 1`。

## 覆盖路线逐步回放

生成覆盖路线后，每条路线的标题栏都有 **「▶ 逐步回放」** 按钮（编辑页右侧「选项覆盖路线」面板内，展开任一条路线即可看到）。点击后进入该路线的逐步回放，再点一次（或「■ 结束回放」）退出：

1. **从起点开始、按路线中的稳定选项 UID 逐步前进**：用「上一步 / 下一步 / 回到起点」控制进度，轨迹同步显示**当前场景、完整变量状态**，以及**下一步选项**（UID、文案、跳转目标与显示条件）；
2. **每一步都用当前草稿重新校验**，而不是直接信任路线生成时的快照：重新求值**选项条件**、校验**目标场景存在**、应用选项与目标场景的**状态赋值**后重新求值**目标场景前置条件**，并把推导出的状态与路线记录的期望状态逐位对比；
3. 草稿相对生成路线时已变化（选项被删 / 被拖动到别的场景、条件翻假、目标消失或改指、赋值变化、起点变化等）时，**停在首个分歧点**，不再继续。分歧面板按步骤给出**原因**与**期望 / 实际**两侧对照：场景与目标、条件取值、完整变量状态，状态不一致时另附逐变量的「路线期望 / 草稿实际」差异表，条件类分歧还复用「未满足条件解释树」提示最少翻转哪些变量；
4. 分歧面板提供 **「↻ 按当前草稿重新生成覆盖路线」** 一键重生成（等价于面板顶部按钮，同样针对编辑中的草稿、不落盘）；
5. 回放**只读草稿，不会保存或修改剧情**；回放进行中继续编辑时，会用最新草稿防抖重新校验，分歧点变早则自动回停到更早的位置；路线结果上的「可能过期」提示逻辑与回放互不影响。

分歧原因类型：`uidMissing`（UID 已缺失，选项可能被删除）、`optionMoved`（UID 被移动到别的场景）、`conditionFalse`（选项条件在当前状态下不成立）、`orphanTarget`（目标为空或场景不存在）、`targetChanged`（跳转目标与路线记录不一致）、`blockedEntry`（目标场景前置条件不成立）、`stateMismatch`（变量状态与期望位图不一致）、`startSceneChanged` / `startBlocked`（起点变化或起点前置不成立）。

`POST /api/coverage/replay` 请求体为 `{ story, route: { options: [UID, ...], path? } }`（草稿不保存），已保存剧情可用 `POST /api/stories/:id/coverage/replay`（请求体即 `route`）。响应要点：`completed`（是否无分歧走完全程）、`total`、`trace.start` / `trace.steps`（每步含场景、UID、条件原文与求值结果、目标、选择前后状态）、`trace.end`、`divergence`（首个分歧点的 `reason` / `atStep` / `uid` / `sceneId` / `target` / `expected` / `actual` / `stateDiffs` / `explain`，无分歧时为 `null`）。分歧属于正常业务结果（HTTP 200），仅参数错误（缺少选项序列、起点无效等）返回 400。

## 伏笔回收路线校验

编辑页右侧的「伏笔回收路线校验」面板回答：**“伏笔埋下之后，是否每条通往设计结局的路线都把它回收了？会不会有玩家一路走到结局，伏笔还悬着？”**

1. 在面板中各选一组 **铺垫场景**（进入后伏笔置为待回收）与 **回收场景**（进入后清除待回收）；两组互斥，同一场景不能既是铺垫又是回收；
2. 点击「运行校验」，后端对 **编辑中的未保存草稿**（不落盘）展开「场景 + 完整变量状态」图，并把 1 位 **待回收标记并入遍历去重键**——状态键 = `(待回收, 场景 ID, 变量位图)`：每次进入铺垫场景置位（起点即铺垫也算），进入回收场景清除，其余场景沿继承。同一 `(场景, 变量状态)` 在两种标记下视为不同节点，“先埋伏笔绕一圈再回收”与“从未埋伏笔”的路线不会被错误合并；状态总数至多翻倍，含任意环路仍必然终止（沿用约 100 万状态安全上限）；
3. **违规判定**：到达 **可达的设计结局**（场景本身没有任何选项的终止具体状态；有选项但全不可走的死局软锁不算）时仍待回收。BFS 按选项步数逐层展开，首个发现的违规即 **最短违规路线**，发现即停（违规路线真实存在，结论确凿）；结果展示该路线的 **选项步数、沿途每个场景到达时的完整变量状态**，并标注铺垫 / 回收事件与每步的待回收状态；
4. **通过判定（缺一即单独提示，不判通过）**：完整探索（未截断）＋ 铺垫可达（遍历中至少进入过一次铺垫场景，否则伏笔从未埋下、校验无意义）＋ 存在可达设计结局（纯循环或只有死局时回收无从校验）＋ 无任何“设计结局且待回收”状态；
5. **单独提示的三种无法判定**：铺垫不可达（`setup-unreachable`）、没有任何可达设计结局（`no-ending`）、状态上限截断（`truncated`，已探索范围无违规也不能断言通过）；起点前置不成立（`start-blocked`）同样单独提示；
6. 校验针对编辑中的草稿；**草稿或铺垫 / 回收选择被修改后，旧结果标记为「可能过期」**，重新「运行校验」即可。

**API 校验（返回 400）**：铺垫 / 回收列表均不得为空、不得含空行或重复项；每个场景 ID 必须存在；两组不得重叠；剧情缺少有效起点。

响应要点：`ok`（是否通过）、`status`（`pass` / `violation` / `setup-unreachable` / `no-ending` / `truncated` / `start-blocked`）、`truncated`、`setupReached`、`pendingStates`（待回收具体状态数）、`endingCount` / `endingStates` / `endings`（可达设计结局明细）、`violation`（违规时含 `endingScene` / `depth` 选项步数 / `path` 场景与选项交替、场景节点带 `state` 与 `pending`、`foreshadow: setup|payoff` 标注 / `finalState`；无违规为 `null`）、`counts`、`knownVars`、`conditionErrors`、`statesExplored`、`maxStates`、`message`。

## 节奏校验（高强度场景连续段）

编辑页右侧的「节奏校验」面板回答：**“会不会有玩家连续经历太多场高强度戏（战斗、追逐、高潮），中间连一个喘息场景都没有？最长允许连续几场？”**

1. 在面板中勾选 **高强度场景**（进入后计入连续段），并设置 **允许的最长连续场景数**（1～10 的整数）；
2. 点击「运行校验」，后端对 **编辑中的未保存草稿**（不落盘），按现有 **选项条件、状态赋值与场景前置条件** 遍历所有可走路线，展开「场景 + 完整变量状态」图，并把 **当前连续高强度计数并入遍历去重键**——状态键 = `(连续计数, 场景 ID, 变量位图)`：每次进入高强度场景计数 +1（起点即高强度则从 1 计起），**进入非高强度场景即清零**，其余沿继承。同一 `(场景, 变量状态)` 在不同连续计数下视为不同节点，所以“绕环一圈累计到第 3 连”与“首次到达只有 1 连”不会被错误合并，**环路中的连续段也须累计**（环上每走一圈高强度场景都推高计数）；连续计数只取 0～上限值，状态总数至多 `场景数 × 2^n × (上限 + 1)`，含任意环路仍必然终止（沿用约 100 万状态安全上限）；
3. **违规判定**：某具体状态的连续计数 **超过允许上限**，即“连续第 上限+1 个高强度场景”被进入（违规在进入时即成立，无论之后通向结局还是循环）。BFS 按选项步数逐层展开，首个发现的超限状态即 **按选项步数最短的超限路线**，发现即停（违规路线真实可走，结论确凿）；结果展示该路线的 **选项步数、沿途每个场景到达时的完整变量状态与连续计数**（高强度场景标注「高强度」，清零节点标注「连续 0 · 已清零」，超限位置标红）；
4. **通过判定**：**完整遍历**（未截断）且没有任何超限状态；响应另给出实际观测到的最长连续段，以及勾选了但在当前草稿中 **不可达的高强度场景**（不参与任何可走路线，提醒作者检查勾选）；
5. **无法判定**：具体状态数达到安全上限被截断时以 `status: 'truncated'` 标明——已探索范围内无超限，但未探索区域可能存在，不能判通过；起点前置不成立（`start-blocked`）同样单独提示；
6. 校验针对编辑中的草稿；**草稿或校验设置（勾选 / 最长连续数）被修改后，旧结果标记为「可能过期」**，重新「运行校验」即可。

**API 校验（返回 400）**：高强度场景列表不得为空、不得含空行或重复项；每个场景 ID 必须存在；`maxConsecutive` 必须是 1～10 的整数（0、11、小数、字符串等均拒绝）；剧情缺少有效起点。

响应要点：`ok`（是否通过）、`status`（`pass` / `violation` / `truncated` / `start-blocked`）、`truncated`、`query`（回显的 `highIntensityScenes` 明细与 `maxConsecutive`）、`maxStreak`（实际观测到的最长连续段）、`reachedHighScenes`（实际进入过的高强度场景；未列入者即不可达）、`violation`（超限时含 `sceneId` / `title` / `streak` 超限连续计数 / `depth` 选项步数 / `path` 场景与选项交替、场景节点带 `state` / `streak` / `highIntensity`、选项边带 `stateAfter` / `streakAfter` / `finalState`；无超限为 `null`）、`counts`、`knownVars`、`conditionErrors`、`statesExplored`、`maxStates`、`message`。

## 结局保证到达（玩家策略求解）

编辑页右侧的「结局保证到达」面板回答：**“有没有一种玩法（玩家策略），无论环境怎么选择，都保证能在有限步内走到指定结局？如果有，每一步该选哪个选项？”**

1. 选择一个 **目标结局场景**（必须是 **无选项场景**；下拉框只列出这类场景），再勾选一组 **环境控制场景**——这些场景中的合法选项由**环境任意选择**（敌对 / 随机 / 不受玩家控制）；**其余场景全部由玩家控制**；
2. 点击「检查可保证性」，后端对 **编辑中的未保存草稿**（不落盘）展开「场景 + 完整变量状态」图（沿用现有选项条件、选项赋值、场景进入赋值与入口前置语义；条件不成立、悬空跳转、入口前置不成立的选项不构成合法边），**选项权重不参与判断**（这里只问“能不能保证”，与概率无关）；
3. **用最小不动点反向扩展（吸引子）判定**：目标结局的全部可达终止状态是已获胜种子（层级 0），随后反复扩展——**玩家状态**只要有至少一个后继已获胜即获胜（玩家可以选择那条边），**环境状态**必须有合法后继、且**全部**后继都已获胜才获胜（环境可以任意选择，必须封死所有出口）；扩展过程单调增长，含任意环路都必然收敛终止；
4. **非目标死局和可无限停留的循环都不算成功**：没有任何合法后继的终止状态（无选项的非目标场景，或有选项但全部不可走的死局软锁）若不是目标，永远不会被标记为获胜；只能永远绕圈的状态也始终不获胜。**有限步保证由层级体现**：每个获胜状态的层级为“使它获胜的后继层级 + 1”，沿推荐选项走层级严格下降，最坏 `起点层级` 步内必然落到层级 0 的目标；
5. **起点已获胜 = 可保证**：列出每个 **获胜玩家状态** 的场景、**完整变量值**、**推荐选项 UID**（含选项文案、跳转目标）与 **层级**；推荐边确定性地选向最低层级后继（平局按 UID 取小，无随机性），且 **必进入更低层级**——这就是一份可直接照玩的获胜策略；
6. **起点未获胜 = 无法保证**：明确显示失败原因并给出一条 **环境反制见证**——`deadend`（环境可把剧情引入非目标死局，附到达死局的最短路线）、`loop`（目标虽可达，但环境可让剧情在循环中无限停留，附进入循环的路线与循环涉及的场景）、`unreachable`（完整探索后目标结局从起点根本不可达）；
7. **无法判定单独提示**：起点场景前置条件不成立（`start-blocked`）或具体状态数达到安全上限被截断（`truncated`）时都 **不下可保证 / 不可保证结论**，已探索区域可能被未探索区域推翻；
8. 求解针对编辑中的草稿；**草稿或求解设置（目标结局 / 环境控制场景勾选）被修改后，旧结果标记为「可能过期」**，重新「检查可保证性」即可。

**API 校验（返回 400）**：缺少目标结局、目标场景不存在、目标场景含有选项（目标必须是无选项场景）；环境控制场景列表中的空行 / 重复项 / 不存在的场景；剧情缺少有效起点。环境控制场景列表可以省略或为空（全部场景由玩家控制），也可以包含目标场景本身（目标状态恒为获胜终止，不受影响）。

请求体 `{ story, query: { targetScene, environmentScenes } }`，例如：

```json
{
  "targetScene": "trueEnding",
  "environmentScenes": ["ambush", "flood"]
}
```

响应要点：`guaranteed`（完整探索时为 `true` / `false`；起点受阻或截断时为 `null`）、`status`（`guaranteed` / `unguaranteed` / `start-blocked` / `truncated`）、`start`（起点状态：`sceneId` / `state` 完整变量值 / `controller` / `rank` 保证层级 / `recommend`）、`winningStates[]`（每个获胜玩家状态：场景、变量值、层级、`recommend`：推荐选项 `uid` / `optionIndex` / `text` / `target` / `nextRank`；截断时为 `null`）、`failure`（无法保证时：`reason` 为 `deadend` / `loop` / `unreachable`、`targetReachable`、`deadendScene`、`witnessPath` 场景与选项交替并带控制方与循环标记、`cycleScenes`；成功时为 `null`）、`counts`（`states` / `transitions` / `playerStates` / `envStates` / `targetStates` / `variables`）、`knownVars`、`conditionErrors`、`statesExplored`、`maxStates`、`message`。

## 变量赋值消费审计

编辑页右侧的「变量赋值消费审计」面板回答：**“每一处场景进入赋值和选项赋值写入的变量值，在再次被赋值或路线结束之前，到底有没有被后续条件读过？”**——帮助作者发现“写了却没人读”的死赋值（可删除，或说明遗漏了引用它的条件分支）。

1. 点击「运行审计」，后端对 **编辑中的未保存草稿**（不落盘）沿现有 **场景、变量状态与合法跳转语义** 展开状态图：**选项条件先于本选项赋值**求值（选项自己的赋值不会被自己的条件读到）、**目标场景进入赋值先于其前置条件**求值（场景自己的进入赋值可能被自己的前置条件读到——即使前置条件最终不成立、入口被挡，这次引用也已经发生）；条件不成立、悬空跳转、入口前置不成立的选项不构成边，其赋值不会执行；
2. **def-use 追踪**：把「每个变量最后由哪处赋值写入」并入遍历去重键——状态键 = `(场景 ID, 每变量最后赋值来源向量)`。由于每处赋值写入的是常量，变量取值位图可由来源向量直接推出；来源向量空间有限，**含任意环路都必然终止**（沿用约 100 万状态安全上限）。每次求值条件时，按 **短路求值** 的真实读取顺序记录被引用变量：`&&` 自左向右、首个为假的合取支之后不再求值，`||` 自左向右、首个为真的析取支之后不再求值，`!` 的操作数总会求值，括号与嵌套任意组合；被短路跳过的子表达式**不构成读取**。例如起点写入 `x=true`、`y=true`，选项条件 `x || y` 实际只读取 `x`，`y` 的赋值不会因此被判为已消费。被实际读取的变量，其当时的来源赋值即被“消费”一次——再次赋值会“杀死”旧值，路线结束（终止场景 / 死局）前未被读取则该次写入作废；
3. **存在性规则**：同一赋值位置在不同可达状态下**只要存在一次有效引用即算已消费**（如 `x || y` 在某条可达路线上 `x=false`、右侧 `y` 被真正求值，`y` 即已消费）；只有完整探索后仍无任何引用，才判定为 **未消费**。条件求值结果不影响引用的成立（条件为 false 时已求值部分的变量也已被读取；**入口受阻前已完成的前置条件求值同样计入**）；读到从未赋值的变量（初始值）不消费任何赋值；
4. 结果 **按赋值位置逐项列出**：`已消费`（附 **到首次引用的最短可走路线**——BFS 逐层展开并对每个位置只保留选项步数最短的见证，路线含沿途场景、每步变量状态与**真实读取发生的位置** / 条件原文）、`未消费`（完整探索下确认写入的值从未被读到，含只出现在被短路分支中的情况）、`未执行`（赋值所在场景从未进入或选项从未可走，附原因）；
5. **截断安全**：状态数超上限被截断时，尚未证实消费的赋值一律标记为 **未知**（`unknown`），**绝不判为未消费**；已证实的消费结论仍然确凿（路线真实可走）；
6. 审计针对编辑中的草稿；**草稿被继续修改后，旧结果标记为「可能过期」**，重新「运行审计」即可。

**API 校验（返回 400）**：剧情缺少有效起点。起点前置条件不成立时以 `status: 'start-blocked'` 单独提示，不产出逐项结果。

响应要点：`ok` / `status`（`ok` / `truncated` / `start-blocked`）、`truncated`、`assignments[]`（每处赋值：`kind`：`scene` 或 `option`、`sceneId` / `sceneTitle`、选项类另带 `optionIndex` / `optionUid` / `optionText`、`assignIndex`、`variable` / `value`、`label` 位置说明、`reachable`、`status`：`consumed` / `unconsumed` / `unknown` / `unreachable`、`reason`（未执行原因）、`reference`（已消费时：`variable` / `depth` 选项步数 / `reader`：引用者（`kind`：`option-condition` 或 `scene-precondition`，含场景、选项序号与条件原文）/ `path` 场景与选项交替并带每步状态 / `stateAtRead` 引用时的完整变量值））、`summary`（`total` / `reachable` / `consumed` / `unconsumed` / `unknown` / `unreachable`）、`counts`、`knownVars`、`conditionErrors`、`statesExplored`、`maxStates`、`message`。

对比结果 `summary` 形如 `{ total, new, fixed, persistent, changed }`；`items` 中每条为 `{ status, issue, before, changes }`（`issue` 为当前问题、`before` 为基线快照；`changes` 为 `['path']` / `['message']`）。每条问题都带 `fingerprint` 字段（16 位 SHA-1）。

路径查询的 `query` 形如：

```json
{
  "targetScene": "throneRoom",
  "constraints": [{ "variable": "hasKey", "value": true }],
  "requiredOptions": ["opt-a1b2c3d4", "opt-e5f6a7b8"],
  "disabledOptions": ["opt-11223344"]
}
```

其中 `requiredOptions` 为 **有序必经选项 UID 数组**（路径必须按数组次序依次经过这些选项，可通过 `path` 中选项边的 `requiredOrder` 确认命中次序），`disabledOptions` 为 **禁用选项 UID 数组**；两者均可省略或为空。校验规则：必经与禁用不得冲突、所有 UID 必须存在、同列表 UID 不得重复，否则返回 400。响应中 `found=true` 时含 `depth` / `path` / `finalState`（且 `unfinishedRequiredOptions` 为空），否则含 `closest`（差异最少状态、缺失变量 `missing`、未完成必经项 `unfinishedRequiredOptions`、最近路径）、顶层 `unfinishedRequiredOptions` 与 `canAssertUnsolvable`（为 `false` 表示因状态上限截断、不能断言无解）。

伏笔回收校验的 `query` 形如（`setups` 为铺垫场景 ID 数组，`payoffs` 为回收场景 ID 数组，均必填、互斥）：

```json
{
  "setups": ["forest"],
  "payoffs": ["witchTower"]
}
```

节奏校验的 `query` 形如（`highIntensityScenes` 为高强度场景 ID 数组，必填；`maxConsecutive` 为允许的最长连续场景数，1～10 的整数）：

```json
{
  "highIntensityScenes": ["forest", "castle"],
  "maxConsecutive": 2
}
```
